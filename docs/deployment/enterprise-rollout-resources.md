# 云基华海 RAG 知识库部署资源与实施步骤

> 状态：实施规划稿｜日期：2026 年 10 月 29 日｜适用范围：一家公司独立部署一套实例

## 一、实施目标与当前边界

首批面向 10–20 名售前、产品和解决方案人员，验证资料入库、授权检索、可信问答、方案编制与 Word 导出的完整流程；通过验收后，再评估向约 100 名员工开放。原始文件、组织权限和业务数据库保留在公司内网；仅经审批、最小化且脱敏的内容允许经受控出口发送到云模型 API。钉钉身份和组织同步按既定优先级安排在核心业务流程稳定之后。

当前仓库已有上述核心业务功能及自动化测试，但仍是受控测试版本。真实模型联调、真实业务质量评估、备份恢复、容量与安全验收尚未完成。[本地 Compose](../../infra/compose/compose.yaml)只启动 PostgreSQL、AIStor、OpenSearch 和解析 Worker 等联调依赖，未包含可直接用于公司的 Core API、Web 和生产安全配置。不得直接复制本地 `.env.example`、单节点 OpenSearch 配置或示例口令到共享环境。

## 二、需要准备的服务和数据存储

| 组件 | 作用 | 初期安排 |
| --- | --- | --- |
| PostgreSQL 17 | 组织、用户、知识空间、ACL、文档版本、任务、方案和审计的权威数据库 | 必需；Flyway 迁移账号与应用运行账号分离，数据盘独立 |
| AIStor 或兼容 S3 的内网对象存储 | 保存原始文件等不可变对象 | 必需；对象数据盘与 PostgreSQL 分开，许可证和应用凭据单独保管 |
| OpenSearch 3.8 | 全文和向量检索投影，可从权威数据重建 | 必需；使用独立 SSD 数据盘，生产配置启用认证与 TLS |
| Spring Boot、Vue、Python 解析 Worker | 业务 API、页面、无状态解析 | 需要构建可部署产物及独立配置；解析 Worker 不持有数据库或对象存储密钥 |
| 云模型 API | 获批后提供生成、Embedding 和重排能力 | 先完成供应商、数据范围、出站域名、密钥和费用审批；未批准时保持关闭 |

当前架构不要求 MySQL、SQL Server、Redis、RabbitMQ 或独立向量数据库。向量能力在[配置样例](../../infra/compose/.env.example)中默认关闭。调用云模型的首期部署不需要 GPU 服务器。

## 三、10–20 人受控试点的服务器起始规格

以下是**资源申请的起始估算，不是已压测的容量承诺**。假设首批约 300–1000 份可信资料、20 人峰值并发场景、业务数据不跨公司共享；大文件、扫描 PDF 和 PNG 的比例升高时，解析资源和磁盘需重新测量。

| Linux 虚拟机 | 建议起始规格 | 放置组件和磁盘 |
| --- | --- | --- |
| 应用节点 | 8 vCPU、32 GB 内存、100–200 GB SSD | 反向代理、Web、Spring Boot、解析 Worker；为解析任务设置内存和并发上限 |
| 数据节点 | 8 vCPU、32 GB 内存 | PostgreSQL 单独预留约 200 GB SSD；AIStor 单独预留约 500 GB SSD；系统盘另计 |
| 检索节点 | 8 vCPU、32 GB 内存、300–500 GB SSD | OpenSearch；JVM 堆从 12–16 GB 起测，保留内存给操作系统缓存 |

三台虚拟机方案便于建立性能和容量基线，但**没有节点级高可用**。OpenSearch 官方建议堆内存约占系统内存的一半，并建议生产集群配置多节点和安全认证；本地 Compose 的 `512 MB` 堆与关闭安全插件设置仅用于开发。[OpenSearch 安装文档](https://docs.opensearch.org/latest/install-and-configure/install-opensearch/index/)

### 正式覆盖约 100 人时的扩容判断

员工总数不等于同时生成方案的人数。若公司可接受单节点故障期间暂停服务，应先用真实负载证明上述资源足够，并完成恢复演练。若要求节点故障后继续服务，规划至少两份应用实例、PostgreSQL 主备、OpenSearch 多节点，以及具备相应高可用能力的对象存储；公司已有的平台能力可复用，不能仅凭员工人数决定采购台数。当前设计中的试点验收基线为业务时段可用性 99.5%、普通检索 P95 小于 3 秒、数据恢复点不超过 24 小时、恢复时间不超过 4 小时；正式服务目标应由业务批准并另行验证。

现有 **AIStor Free** 许可证支持单节点使用，但不提供分布式部署、内置复制、AIStor 服务端静态加密功能或 SLA。若贵司正式环境要求这些能力，应先评估已有企业对象存储或相应许可证，再确定服务器采购。许可证文件继续保存在仓库外的 `E:\git_secrets\Elite-RAG\minio.license`，只读挂载，不进入镜像、Git 或工单。[MinIO AIStor 许可说明](https://docs.min.io/aistor/operations/licenses/)

### 磁盘容量的定型方法

1. 统计各类文件的数量、实际 GB 数、平均与最大文件大小、扫描件比例、保留版本数，以及未来 12–24 个月增量。
2. 先导入 100–200 份具有代表性的文件，分别记录 PostgreSQL、AIStor、OpenSearch 的占用和解析耗时，再按预期增长量扩容并保留空闲余量。
3. 备份容量和保留周期单独计算；PostgreSQL 与对象存储必须能在隔离环境恢复，OpenSearch 从权威数据重新投影。若需要时间点恢复，应设计 PostgreSQL 基础备份与 WAL 归档并实际演练。[PostgreSQL 备份与恢复文档](https://www.postgresql.org/docs/17/continuous-archiving.html)

## 四、网络、安全和运维准备

- 用户只通过内网 HTTPS 入口访问 Web/API；PostgreSQL、OpenSearch、AIStor API 和解析 Worker 仅开放给必要服务，不直接面向普通用户。
- 云模型请求只从受控出口访问审批域名。供应商审批须明确可发送的数据密级、脱敏规则、留存与训练使用条款、额度和异常停用方式。
- 生产密钥由公司密钥系统注入；数据库迁移、运行和对象存储应用身份分离。备份存放在故障域外，监控容量、失败任务、模型费用、许可证状态和权限拒绝。
- 测试、预生产和正式环境至少逻辑隔离；真实客户资料不能直接复制到测试或性能环境。先用合成或已获批准的脱敏数据做验证。

## 五、实施步骤与交付门槛

| 阶段 | 主要工作与责任人 | 完成判据 |
| --- | --- | --- |
| 1. 业务准备 | 业务负责人确定试点场景与 10–20 名用户；知识管理员清理、分类、授权约 300–1000 份资料；售前和产品人员提供脱敏需求、认可方案及人工标注问题 | 有资料责任人、授权范围、评测样本和现有耗时基线 |
| 2. 环境与审批 | IT 准备隔离 Linux 环境、持久盘、证书、备份和监控；安全、法务、业务共同审批云模型与数据边界 | 密钥与网络规则到位；对象存储许可证及高可用要求已决定 |
| 3. 部署与联调 | 开发和运维构建 Core API/Web/Worker 部署产物，执行 Flyway 迁移，部署 PostgreSQL、AIStor、OpenSearch，完成登录、上传、解析、发布、检索、生成和 Word 导出联调 | 受控环境中的真实服务链路完成；无权用户无法查看或下载资料 |
| 4. 上线前验收 | 测试与安全人员执行权限负样本、质量评测、提示注入、20 人并发、故障注入、备份恢复和费用监控 | 关键事实引用覆盖率 ≥90%、人工抽检支持准确率 ≥95%、权限越权 0；恢复与性能达到批准目标 |
| 5. 小范围试点 | 10–20 名用户使用 2–4 周，知识管理员每周复盘错误，业务负责人对比人工基线 | 初稿平均耗时降低目标 ≥50%、周活跃率目标 ≥60%、系统生成或复用内容使用率目标 ≥70%；决定扩大、延长试点或停止 |
| 6. 扩大使用 | 根据实测并发和可用性要求扩容；再完成钉钉身份和组织同步及公司级运维交接 | 完成身份、权限、监控、恢复和变更流程的交接后逐步开放约 100 名员工 |

以上数值是项目既定的**试点目标**，尚未通过真实客户样本测量；详细口径见[方案反馈与试运行门槛](../runbooks/solution-feedback-pilot-gates.md)。任何越权或恢复失败都应阻止扩大使用。

## 六、资源申请前需要确认的输入

为将起始规格改成采购清单，请业务与 IT 共同填写：① 首批和两年预计文件总量（份数与 GB）；② 各格式比例、扫描件比例和单文件最大值；③ 峰值同时在线、上传、检索和生成任务数；④ 可接受停机时间及数据丢失上限；⑤ 公司是否已有 PostgreSQL 主备、企业级 S3、容器平台、备份和密钥系统；⑥ AIStor Free 是否满足资料密级与高可用要求。拿到这些数据并完成代表性导入与压测后，再确定最终 CPU、内存、磁盘和节点数量。
