# 知识底座运行与恢复手册

## 1. 文档定位与当前可用范围

本手册描述知识底座的目标运行流程，并明确当前实现可以执行到哪一步。2026-09-24 的代码已通过业务层自动化验收，但 PostgreSQL/Flyway、MinIO、生产依赖注入、真实钉钉租户和前后端联调尚未完成。因此：

- 可以在开发机运行单元、契约、业务验收、前端构建和浏览器测试；
- 可以单独启动 Python 解析 Worker 并检查健康状态；
- 不得把当前代码部署为生产或试点系统；
- 不得上传真实客户资料，不得打开云模型出网，不得创建 `pilot-foundation-v1` 标签。

下文中标记为“投产前待装配”的步骤是操作规范，不代表当前仓库已经提供相应端点、Schema 或脚本。

## 2. 角色与变更控制

投产前必须实名确认以下角色，不能以开发人员默认代任：

| 角色 | 责任 | 当前状态 |
| --- | --- | --- |
| 业务负责人 | 资料准入、发布与效果验收 | 待确认 |
| 数据负责人 | 密级、保留期、删除与出网审批 | 待确认 |
| 平台负责人 | 部署、备份、恢复、容量与告警 | 待确认 |
| 安全负责人 | 钉钉权限、密钥、日志、漏洞和事件响应 | 待确认 |
| 值班人员 | 日常健康检查、失败重放与升级 | 待确认 |

生产变更需具备工单、回滚方案、执行人和复核人。密钥轮换、数据恢复、物理删除及 ACL 批量变更必须双人复核。

## 3. 启动前检查

### 3.1 当前开发验收

```powershell
$env:JAVA_HOME = 'C:\Program Files\Zulu\zulu-21'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1
corepack pnpm --dir apps/web exec playwright test e2e/knowledge-foundation.spec.ts
```

所有命令退出码必须为 0。浏览器测试当前使用 mock HTTP，只能证明界面状态与权限位消费正确，不能证明后端已经联通。

Python 门禁会安装 `parsing` extra，并使用真实 Docling 解析固定 Markdown 和数字 PDF。Office、扫描 PDF 与 PNG 的真实回归样本尚未准入，不能把当前结果外推为全部格式质量达标。

### 3.2 投产前待装配检查

以下项目全部确认后才允许启动完整系统：

- PostgreSQL 迁移已在空库和升级库验证，连接使用最小权限账户；
- MinIO 存储桶、版本控制、服务端加密、生命周期和回收器已验证；
- 恶意软件扫描引擎可用，失败时默认拒绝上传；
- 钉钉应用权限、回调地址和组织数据范围已审批；
- Java API、Python Worker 和 Web 的镜像均以固定摘要发布；
- 所有密钥来自企业密钥系统，不存在于镜像、环境样例、日志或 Git；
- 内网 DNS、TLS、服务间认证、出网默认拒绝和允许列表已验证；
- 备份恢复演练达到已批准的 RPO/RTO；
- 真实样本文档和基准问答已由数据负责人准入。

## 4. 启动、停止与健康检查

### 4.1 解析 Worker

开发机启动：

```powershell
uv sync --project workers/document-parser --extra parsing --locked
uv run --project workers/document-parser uvicorn parser_worker.app:app `
  --app-dir workers/document-parser/src --host 127.0.0.1 --port 8001
```

检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8001/health
```

期望返回 `status=ok`、`service=document-parser`。该健康检查只代表进程可响应，不代表 Docling 已用真实文件完成解析；发布前还必须运行契约与样本测试。

停止时向前台进程发送 `Ctrl+C`。生产环境应先从服务发现或负载均衡摘除实例，等待当前请求在超时上限内结束，再发送终止信号；超过宽限期才强制终止。Java 租约过期后可由其他 Worker 接管。

### 4.2 Web

开发机启动：

```powershell
corepack pnpm --dir apps/web dev
```

构建产物检查：

```powershell
corepack pnpm --dir apps/web build
```

当前 Web 依赖 mock HTTP 验收。生产部署前必须完成真实 API 基址、钉钉会话、CSRF/CORS、安全响应头和前后端字段对齐。

### 4.3 Java Core API（投产前待装配）

目标健康端点为 `/actuator/health`，但当前仓库缺少可运行的数据源和业务 Bean 装配。补齐 Task 2 后，启动顺序应为：PostgreSQL → MinIO → 恶意扫描 → Parser Worker → Core API → Web；停止顺序相反，并先停止新上传和发布入口。

不得使用“进程存在”替代健康检查。完整就绪检查至少应覆盖数据库迁移版本、对象存储读写探针、解析服务契约版本、审计写入和钉钉依赖降级状态。

## 5. 钉钉组织同步（投产前待装配）

领域服务已经具备完整快照校验、原子对账和停用用户会话失效规则，但尚无定时任务、管理端点或持久化适配器。

正式流程应为：

1. 使用只具备必要通讯录权限的钉钉应用拉取全部分页；
2. 校验分页游标无循环且页数不超过上限；
3. 只有完整快照才进入 `OrganizationSyncService.synchronize`；
4. 在一个数据库事务中更新部门、用户和隶属关系；
5. 对停用或移除用户提升会话版本并禁止重新签发；
6. 记录开始时间、结束时间、计数、上游请求 ID 和结果，不记录手机号、姓名全文或 Token；
7. 对账失败保留上一份完整快照，不执行“缺失即删除”。

每日检查用户数、部门数、停用数与钉钉后台差异。突然大幅减少时立即阻断同步并升级给安全与数据负责人。

## 6. 失败解析任务重放（投产前待装配）

当前已实现租约、过期接管、尝试次数、失败码和幂等派生内容替换；尚无 PostgreSQL 队列适配器和管理端点，不能直接在生产数据库手工改状态。

重放原则：

- 只重放 `retryable=true` 或经人工确认已修复根因的任务；
- `ENCRYPTED`、不支持格式、恶意内容或超限文件不得自动重试；
- 保持原 `DocumentVersionId`、Blob 校验和与解析契约版本；
- 每次重放生成新租约并增加 attempt，不复用旧 lease token；
- 显式可重试错误或 Worker 连续崩溃造成的租约过期，达到批准的最大尝试次数后都进入人工处理，不得无限循环；
- 成功后只能推进到“待审核”，不得自动发布；
- 重放动作与结果写入审计，只允许白名单元数据。

在管理端点和持久化仓储完成前，禁止编造 SQL 直接修改任务表。

当前代码已实现三次尝试上限和 30 秒起步的指数退避端口；精确阈值在真实负载基线后配置化。PostgreSQL 适配器必须让 `nextAttemptAt` 成为原子领取条件。

## 7. 手工恢复

### 7.1 Worker 在解析中崩溃

确认实例已停止、临时文件由隔离区清理任务回收。等待租约到期，由新 Worker 原子领取；不得手工复制旧 lease token。检查同一版本只有一个最终成功状态，派生内容以版本键幂等替换。

### 7.2 解析成功但业务状态未推进

先核对审计中是否存在 PARSE 成功事件，再检查派生内容、任务状态和文档版本是否同一事务提交。若三者不一致，停止发布入口、保留证据并由平台负责人执行经评审的修复脚本。当前尚无数据库 Schema，修复脚本必须在 Task 2 之后按真实表结构编写和演练。

### 7.3 Blob 已写入但文档创建失败

Blob 只登记为延迟清理候选。回收器必须在数据库中原子确认没有已提交引用和上传预留后才能物理删除，禁止请求线程直接删除同 SHA-256 对象。

### 7.4 审计写入失败

上传、发布、查看、下载和归档与审计应在业务事务中保持一致。审计不可用时写操作失败并告警；不得通过关闭审计恢复业务。读操作是否降级必须由安全负责人书面批准，当前实现选择不静默跳过审计。

业务层验收使用内存端口，不能证明 Spring 代理和 PostgreSQL 表发生真实回滚。Task 2 必须增加故障注入集成测试：分别让文档、派生节点、任务和审计写入失败，并断言同一事务内所有表均恢复原状；该测试通过前不得把“审计原子性”标为完成。

## 8. 归档与删除

归档是当前唯一允许的业务下线方式。调用 `POST /api/v1/knowledge-spaces/documents/{documentId}/archive` 后，文档对授权和未授权用户都不再出现在生产列表中，详情访问统一隐藏为 404，审计记录继续保留。

物理删除尚未实现。未来删除必须满足保留期、诉讼保全、引用计数、备份周期和双人审批；内容寻址 Blob 仅在所有文档版本、上传预留和恢复窗口均无引用时清理。禁止直接从 MinIO 控制台删除对象。

## 9. 备份与恢复（投产前待装配）

RPO/RTO 尚未由业务负责人批准，不能自行填写。目标备份集至少包含：

- PostgreSQL 全量备份、WAL/等价增量与 Flyway 版本；
- MinIO 对象版本和存储桶配置；
- 不含密钥明文的应用配置与镜像摘要；
- 审计数据及其完整性校验；
- Parser JSON Schema 与发布版本。

恢复顺序为 PostgreSQL → MinIO → 配置/密钥引用 → Parser → Core API → Web。每季度至少执行一次隔离环境恢复演练，验证数据库记录、Blob SHA-256、当前发布指针、ACL、审计链和代表性下载，不以“备份任务成功”代替恢复验证。

## 10. 密钥轮换（投产前待装配）

轮换对象包括钉钉 App Secret、数据库口令、MinIO 凭据、服务间 TLS 证书、会话签名密钥和获批云模型 API Key。

标准流程：创建新版本 → 在非生产验证 → 双密钥短暂并行 → 滚动更新服务 → 验证健康与审计 → 吊销旧版本 → 检查旧密钥无调用。任何日志和工单只记录密钥版本或指纹，不记录明文。发现泄漏时立即吊销，不等待常规窗口，并按安全事件处理。

## 11. 日志脱敏与审计检查

允许记录：任务 ID、文档/版本 UUID、错误码、尝试次数、耗时、服务版本、调用结果和经批准的主体 ID。

禁止记录：文件正文、解析节点文本、文件字节、Authorization/Cookie、钉钉 access token、云模型 API Key、数据库/MinIO 密钥、手机号、身份证号、客户名称全文和未脱敏文件名。

审计元数据实行代码白名单。每周抽查上传、解析、发布、查看、下载、归档事件是否完整，抽查越权访问没有泄露资源存在性。日志平台访问遵循最小权限并保留查询审计。

## 12. 发布准入与回滚

只有以下条件全部满足才能创建试点标签：

- Task 0 的负责人、基线、可信资料和模型审批齐全；
- Task 2 的 PostgreSQL/MinIO/Flyway 及集成测试完成；
- Java、Python、Web、浏览器和 Compose 配置验证全部通过；
- 真实钉钉租户、恶意扫描和前后端端到端测试通过；
- 备份恢复、密钥轮换和日志脱敏完成演练；
- 独立安全与代码评审无阻断问题。

回滚优先使用上一固定镜像和向后兼容 Schema，禁止回滚已执行的数据迁移文件。若新版本可能错误发布或越权，立即关闭上传/发布入口并从负载均衡摘除 Core API；保留数据库、对象和审计证据，禁止用清库方式恢复。
