# 方案需求整理与大纲候选实施计划

## 目标与当前边界

在已批准的方案工作台设计上，为员工提供有来源的需求整理建议和已确认需求的大纲候选。模型输出先供人工检查，不自动确认需求、大纲或定稿。当前生产装配仍只支持人工录入；本计划不得被视为模型提案入口已交付或生产准入。

现有 `SolutionWorkbenchService` 有提案领域方法，但 `local` 装配注入的模型端口会直接拒绝，HTTP 和页面也没有入口。模型请求只含既有需求条目，需求提案没有检索证据，因此首版只能整理输入中已有来源的需求；不能把它称为从新上传文件自动提取需求。真正的文件提取须另设受控检索与来源快照。

## 选定路径

采用“只读生成候选 → 人工审阅 → 现有修订命令保存 → 异人确认”。不直接把模型结果写为当前版本；已有自动写入的领域提案方法继续不对外暴露。候选只允许引用输入需求里的精确 `DocumentVersionRef + SourceLocator`；模型不能新增文档、版本或定位。大纲候选必须绑定当前已确认需求的版本 ID 和方案修订号。

模型调用不放在持有方案数据库锁的事务内。候选请求以操作者、方案、动作、需求版本、修订号和客户端幂等键建立持久化记录；同键同输入返回同一结果，同键异输入冲突，进行中的同键请求不重复调用模型。模型调用超时或崩溃后按租约恢复，不能假报成功，也不能在结果不明时盲目重复计费。存储只保留必要的候选和脱敏审计元数据，禁止记录完整出站提示词或密钥。

## 实施顺序

1. **来源防伪。** 先写失败测试，证明模型提案可携带输入外的文档版本或定位；再在领域层拒绝此类提案，确保拒绝前不写版本。该防线在本轮实施。
2. **模型协议。** 为 `requirements/v1`、`outline/v1` 增加固定 JSON Schema 和严格解析；校验结构、数量、顺序、风险类型、来源白名单与字段长度。动态出站文本沿用统一脱敏策略。用本地假网关验证无效输出、敏感内容和零外发拒绝。
3. **持久化候选。** 新增候选状态、租约、输入指纹与结果存储；实现事务内登记和完成，模型调用在事务外；并发、重试、超时、撤权及需求版本变化均失败关闭。真实 PostgreSQL 集成测试覆盖重启恢复和同键并发。
4. **业务 API。** 生成和读取候选时重新检查空间动作权限、当前需求版本、来源发布及 ACL；禁用模型时返回明确的能力不可用错误。应用候选复用现有 `reviseRequirements` / `reviseOutline`，仍需人工确认。
5. **中文页面。** 显示候选与当前内容的差异、引用来源和模型状态；提供“采纳为待确认修订”按钮，冲突时保留用户编辑内容。桌面与窄屏都能操作，不把模型建议显示为已确认事实。
6. **验证与交付。** Java 领域/真实 PostgreSQL/假网关测试、前端单元与浏览器测试、统一验证脚本通过后，更新运行手册并提交本地 Git commit。真实审批模型和真实脱敏样本仍需单独验收。
