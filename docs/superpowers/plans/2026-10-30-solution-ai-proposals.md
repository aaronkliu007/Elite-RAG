# 方案需求整理与大纲候选实施计划

## 目标与当前边界

在已批准的方案工作台设计上，为员工提供有来源的需求整理建议和已确认需求的大纲候选。模型输出先供人工检查，不自动确认需求、大纲或定稿。候选 API 和中文审阅页面已接入 `local` 装配；真实审批模型与真实资料仍需独立验收，不代表生产准入。

现有 `SolutionWorkbenchService` 自动写入提案方法继续不对外暴露，新入口通过 `SolutionProposalService` 生成只读候选。首版只整理已有需求及来源；真正的文件提取须另设受控检索与来源快照。

## 选定路径

采用“只读生成候选 → 人工审阅 → 现有修订命令保存 → 异人确认”。不直接把模型结果写为当前版本；已有自动写入的领域提案方法继续不对外暴露。候选只允许引用输入需求里的精确 `DocumentVersionRef + SourceLocator`；模型不能新增文档、版本或定位。大纲候选必须绑定当前已确认需求的版本 ID 和方案修订号。

模型调用不放在持有方案数据库锁的事务内。候选请求以操作者、方案、动作、需求版本、修订号和客户端幂等键建立持久化记录；同键同输入返回同一结果，同键异输入冲突，进行中的同键请求不重复调用模型。模型调用超时或崩溃后按租约恢复，不能假报成功，也不能在结果不明时盲目重复计费。存储只保留必要的候选和脱敏审计元数据，禁止记录完整出站提示词或密钥。

## 实施顺序

1. **来源防伪（已完成）。** 失败测试证明模型提案可携带输入外的文档版本或定位；领域层现已拒绝此类提案，拒绝前不写版本。
2. **模型协议（已完成协议层，未开放业务入口）。** `requirements/v1`、`outline/v1` 已有固定 JSON Schema 和严格解析；校验结构、数量、顺序、风险类型、来源白名单与字段长度。动态出站文本沿用统一脱敏策略；本地假网关测试覆盖无效输出、敏感内容和零外发拒绝。
3. **持久化候选（已完成）。** V017 与 PostgreSQL 存储器提供候选状态、数据库时钟租约、输入指纹、结果 JSONB、同键唯一登记和终态条件写入。`SolutionProposalService` 在登记与完成两个短事务之间调用模型；调用前后复核权限、来源、需求版本和修订号，只保存候选，不修改当前方案。关闭模型时拒绝创建候选；调用结果不确定时同键不自动重试，租约到期标记 `INDETERMINATE`。真实 PostgreSQL 测试覆盖并发、重建后读取和租约边界；应用层测试覆盖重放、来源撤销、大纲确认前置条件与不确定结果。
4. **业务 API（已实现）。** 生成和读取候选时重新检查空间动作权限、当前需求版本、来源发布及 ACL；禁用模型时返回明确的能力不可用错误。应用候选复用现有 `reviseRequirements` / `reviseOutline`，仍需人工确认。
5. **中文页面（已实现）。** 对比当前内容与候选，展示引用来源和模型状态；勾选审阅后可“采纳为待确认修订”，冲突时保留用户编辑内容。按登录用户保存原请求键，未登记的请求可用原键重发，已有请求不重复调用模型。桌面与窄屏均通过浏览器验证。
6. **验证与交付（本地完成）。** 统一验证脚本通过：Java 721 项、前端 48 项、解析 Worker 16 项测试，构建与静态检查通过；浏览器回归 14 个场景通过，并检查桌面及窄屏。运行说明见 `docs/runbooks/solution-model-proposals.md`。真实审批模型和真实脱敏样本仍需单独验收。

## 编排阶段实施记录

- 后台恢复沿用已有 Worker 的固定延迟方式：总开关及独立恢复开关同时启用，默认每 30 秒扫描 100 条。扫描只使用数据库租约标记 `INDETERMINATE`，不执行模型；锁定记录跳过、异常后下一周期继续。查询恢复仍保留。

- 候选模型请求禁用 HTTP 层自动重试；超时或连接结果不明时保留不确定状态，避免未经确认再次计费。既有其他模型调用维持原有重试策略。
- 网关已明确返回的无效响应、策略拒绝、认证失败和限流拒绝记为 `FAILED`；不保留供应商错误详情。
- 代码审查发现上述两处边界问题后，先用失败测试复现，再修复并通过定向测试；复审未发现这两处修复的剩余问题。
