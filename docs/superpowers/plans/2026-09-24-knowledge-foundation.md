# Knowledge Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a releasable knowledge foundation in which authenticated users can upload, parse, catalog, authorize, publish, view, archive, and audit immutable enterprise documents.

**Architecture:** The Spring Boot modular monolith owns identity, ACL, knowledge lifecycle, storage orchestration, and audit. A stateless Python worker converts approved files into a versioned canonical JSON document; PostgreSQL remains authoritative and MinIO stores immutable blobs. The Vue UI exposes only workflows already protected by server-side authorization.

**Tech Stack:** Java 21, Spring Boot 4.1.1, Maven, Spring Security, Spring Data JPA, Flyway, PostgreSQL, MinIO Java SDK, Testcontainers, Python 3.12+, FastAPI, Docling, PaddleOCR, pytest, Vue 3, TypeScript, Pinia, Vue Router, Vitest, Playwright, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-09-24-enterprise-rag-solution-generation-design.md`

## Global Constraints

- Package root is `com.yunjihai.rag`; changing it requires an ADR before scaffolding.
- REST APIs are rooted at `/api/v1` and return RFC 9457 `ProblemDetail` errors.
- IDs are UUIDv7-compatible UUID values generated by the application; timestamps are UTC `Instant` values.
- PostgreSQL is authoritative; MinIO objects are immutable and addressed by object key plus SHA-256.
- Authorization is default-deny; knowledge-space scope is the upper bound and a document may only narrow it.
- Python receives object streams and job metadata, never database credentials or user authorization context.
- Only `PUBLISHED` current versions are user-visible; drafts and failed parses never leak through list or download APIs.
- Java 21 and Linux containers are the production baseline.

## Review Focus

- Re-uploading identical bytes must reuse the stored blob without creating duplicate active versions; Task 6 pins this behavior.
- A parser crash or malformed result must leave the version non-published and preserve the original file for manual recovery; Tasks 7 and 8 pin this behavior.
- A user removed from a department must lose document access after the next organization sync and permission-cache invalidation; Task 4 pins this behavior.
- A disabled DingTalk user must be unable to continue with an existing session; Task 4 pins this behavior.
- Oversized, unsupported, password-protected, or malicious-looking files must be rejected before publication and must not leave an orphaned blob; Task 6 pins this behavior.
