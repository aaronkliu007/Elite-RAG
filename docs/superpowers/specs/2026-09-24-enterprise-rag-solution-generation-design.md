# 云基华海企业级 RAG 方案生成系统设计

- 状态：已确认，待内部书面评审
- 日期：2026-09-24
- 首期周期：10–14 周
- 首期用户：售前/销售与产品/解决方案联合试点，10–20 人
- 总体路线：模块化自建业务系统，复用成熟基础组件

## 1. 背景与目标

云基华海约 100 人，具有 13 年传统软件开发经验。公司资料分散在共享目录、业务系统、企业协作工具和员工个人设备中，主要格式包括 Word、Excel、PDF、PPT、Markdown 和 PNG。

首期聚焦“历史方案复用与新方案辅助生成”，不建设通用聊天机器人。目标是跑通如下可验收闭环：

1. 用户上传客户需求或填写结构化项目背景。
2. 系统提取目标、范围、约束和交付物，由用户确认。
3. 系统从用户有权访问的历史方案、案例、产品能力和标准模板中检索证据。
4. 系统生成大纲，由用户确认后逐章生成草稿。
5. 关键事实带可定位的原文引用，证据不足时系统拒绝编造。
6. 用户审阅、修改、定稿并导出 Word，反馈重新进入评估和知识治理闭环。

## 2. 成功指标

### 2.1 业务指标

- 方案初稿平均耗时比试点基线降低至少 50%。
- 试点用户周活跃率不低于 60%。
- 至少 70% 的试点方案使用系统生成或复用内容。
- 试点用户能完成从需求录入到 Word 导出的完整链路。

### 2.2 质量指标

- 关键事实引用覆盖率不低于 90%。
- 人工抽检的引用支持准确率不低于 95%。
- 黄金检索集上的 Recall@10 和 nDCG@10 达到项目在第 0 阶段设定的基线。
- 金额、工期、客户名称、性能指标和法律承诺等高风险字段必须人工确认。

### 2.3 安全与工程指标

- 权限自动化用例通过率 100%，不发生跨部门、跨项目越权。
- 所有模型调用可追溯至用户、方案、证据、提示词和模型版本。
- 长任务能在服务重启后恢复，已确认章节不丢失。
- 业务时段可用性试点基线为 99.5%；普通检索 P95 不超过 3 秒。
- PostgreSQL 与对象存储 RPO 不超过 24 小时，RTO 不超过 4 小时。

## 3. 首期范围

### 3.1 范围内

- Word、Excel、PDF、PPT、Markdown 和 PNG 的人工批量上传。
- 文件扫描、哈希去重、版本管理、结构解析、OCR、人工编目和发布。
- 行业、产品、客户、项目、年份、密级、部门、版本状态等元数据。
- 钉钉 SSO、组织架构同步，以及部门、角色、知识空间和单文档授权。
- 全文与向量混合检索、RRF 融合、Reranker、引用定位。
- 需求结构化、大纲确认、分章生成、引用核验、在线编辑、版本比较和 Word 导出。
- 采纳、修改、退回原因和离线评估。

### 3.2 范围外

- 自动接入所有员工个人电脑、聊天记录和历史资料。
- 无人审核生成并对外发送方案。
- 通用知识问答、报表生成、文档评审和研发问答。
- 复杂知识图谱、公司自有大模型训练和自主 Agent 操作业务系统。
- 对所有 Excel 公式、PPT 动画和复杂图表的完美语义还原。

## 4. 总体架构

系统采用混合部署。原始文档、解析结果、索引、权限、方案和审计数据全部保留在内网。只有经身份校验、ACL 过滤、敏感检测、脱敏和上下文限额处理后的最小证据包允许发往已审批的云模型 API。

### 4.1 可部署单元

1. **Web 前端**：Vue 3 + TypeScript，提供知识管理、方案工作台、引用查看和管理界面。
2. **Spring Boot 核心应用**：Java 21，负责业务与 AI 编排。
3. **Python 能力 Worker**：只负责文档解析、OCR 和本地模型推理等无状态计算，不判断权限，不承载业务事实。
4. **OpenSearch**：可重建的全文、向量和元数据检索投影。
5. **数据基础设施**：PostgreSQL、MinIO 或兼容 S3 的内网对象存储，以及可选 Redis。

首期不拆分大量微服务。Spring Boot 以模块化单体起步，各领域通过稳定内部接口隔离。

### 4.2 Java 与 Python 边界

Spring Boot 负责钉钉身份、ACL、知识生命周期、方案工作流、检索编排、模型网关、提示词、生成、引用、评估和审计。Spring AI 可用于模型适配和局部 RAG 能力，但公司自定义的领域接口是稳定边界。

Python Worker 优先封装 Docling、PaddleOCR 等 Python-first 能力，对外输出统一文档 JSON。如果 Embedding 和 Reranker 均使用云 API，Python 仅承担解析和 OCR。Node.js 不进入后端主链路。

## 5. 核心数据模型

- **KnowledgeSpace**：知识边界、负责人、默认密级和最大可见范围。
- **Document**：逻辑知识资产，与具体文件版本分离。
- **DocumentVersion**：不可覆盖的文件版本，包含哈希、有效期和生命周期状态。
- **DocumentNode**：章节、段落、列表、表格、图片和幻灯片等结构化节点。
- **RetrievalChunk**：从节点生成的检索单元，包含父子关系、来源定位、ACL 投影和有效期。
- **AclEntry**：用户、部门、角色、项目组等主体的授权。
- **SolutionTemplate**：方案类型、章节结构、必填字段和风险规则。
- **Solution / SolutionVersion / SolutionSection**：方案、版本和可独立生成的章节。
- **EvidenceCitation**：方案事实与原文节点、页码、表格或幻灯片的映射。
- **GenerationRun / ModelCall**：检索、提示词、模型、输入摘要、输出、耗时和费用。
- **Feedback / EvaluationCase**：采纳、修改、退回、错误分类、标准问题和期望证据。
- **AuditEvent**：上传、查看、检索、生成、导出、授权和删除。

## 6. 权限设计

首期使用“默认不可见 + 白名单授权”，不引入显式拒绝规则。用户的有效身份集由钉钉用户 ID、所属部门及上级部门、系统角色和项目组组成。

知识空间确定最大可见范围，文档权限只能进一步收紧，不能突破空间边界。最终可见范围为：

`knowledge-space grant ∩ document grant ∩ active publication state`

权限执行包含两道校验：

1. 检索前将用户有效身份转换为 OpenSearch 过滤条件。
2. 返回证据前，Spring Boot 根据 PostgreSQL 事实再次校验文档权限。

钉钉首次同步完整组织架构，后续定时增量同步；具备条件后增加事件回调。搜索时不实时调用钉钉。离职或停用用户立即禁止登录并使会话失效。

## 7. 文档采集与处理

入库流程为：

`upload -> malware/type/size check -> hash/dedup -> parse/OCR -> normalize -> semantic split -> catalog -> index -> review -> publish`

格式策略：

- Word、PDF 和 Markdown 按标题层级、段落和列表切分，保留父章节。
- PPT 以单页为基本单元，关联标题、备注和前后页主题。
- Excel 识别工作表、表格区域、表头和数据行；大表同时生成表级摘要、分组行片段和原单元格定位。
- 扫描件和 PNG 经 OCR 处理，保留页码、坐标、原图和置信度。
- 切分参数可配置，不使用全格式统一固定字数切分。

文档生命周期为“草稿、待审核、已发布、已归档”。只有已发布的当前有效版本进入生产检索。普通删除先进入回收站，权限层立即阻断访问，后台完成对象和索引清理。

## 8. 检索与生成

### 8.1 检索流程

1. 根据客户需求、章节目标和已确认大纲生成检索问题。
2. 加入行业、产品、方案类型、年份和权限过滤。
3. BM25 与向量检索并行召回。
4. 使用 RRF 融合候选结果。
5. 使用 Reranker 精排，去重并限制单一文档占比。
6. 组装带来源定位的证据包。
7. 返回前再次校验文档权限和有效状态。

首期从“BM25 与向量各召回 50 条，融合后重排 30 条，最终提供 8–15 个证据片段”开始评估。这些是可配置起点，由黄金集结果决定正式值。

### 8.2 生成流程

`requirements extraction -> human confirmation -> outline generation -> human confirmation -> per-section retrieval -> generation -> citation verification -> cross-section consistency -> human finalization`

每个章节保存需求版本、大纲版本、检索查询、候选结果、最终证据、模型版本、提示词版本、原始输出、用户修改和最终文本。

事实性陈述必须绑定引用。引用核验不仅检查引用是否存在，还要检查证据是否支持陈述。无证据内容只能标记为建议或待确认；证据不足时不生成公司能力、客户案例或硬性承诺。

## 9. 模型网关

业务代码不直接依赖云模型 SDK。Spring Boot 内的模型网关提供统一接口，处理：

- 大语言模型、Embedding、Reranker 和视觉/OCR 服务适配。
- 供应商、模型、地域、数据保留和不用于训练的准入规则。
- 敏感检测、脱敏、上下文限额、超时、限流、重试和备用模型。
- 用户、场景、输入摘要、输出、耗时、Token 和费用审计。

只有模型网关允许访问外网模型 API，其他服务默认无互联网出口。

## 10. 任务状态与异常处理

解析、索引和章节生成任务都使用显式状态机：

`PENDING -> RUNNING -> SUCCEEDED | FAILED_RETRYABLE | FAILED_MANUAL | CANCELLED`

- 任务具有幂等键，重复上传、超时和重启不产生重复版本、索引或费用。
- 临时故障按退避策略重试；损坏、加密或无法识别的文件进入人工处理队列。
- 解析失败时保留原文，不建立不完整索引。
- 模型不可用时保留任务和已确认章节，允许重试或切换已审批备用模型。
- OpenSearch 不可用时仍保存原文和元数据，索引任务稍后恢复。
- 定时对比 PostgreSQL、对象存储和 OpenSearch，修复不一致数据。

首期若公司已有 RabbitMQ，使用现有消息队列；否则使用 PostgreSQL 任务表和安全锁机制，不因试点额外引入新中间件。

## 11. 安全设计

- 上传文档作为不可信输入，扫描恶意文件、隐藏文本、零宽字符、异常指令和可疑外链。
- 模型输入严格分隔系统指令、用户需求和检索证据；文档内容只能作为数据。
- 首期模型无权发送邮件、修改业务系统或调用任意工具。
- 模型输出作为不可信内容，导出前清洗 HTML、脚本和外部资源。
- 高密级文档可配置为禁止调用外部模型。
- 密钥使用专用密钥管理方式，日志不记录明文密钥和完整敏感正文。
- 定期执行越权、提示注入、知识投毒、路径穿越、恶意文件和输出注入测试。

## 12. 可观测性与评估

统一追踪 ID 贯穿 Web、Spring Boot、Python Worker、OpenSearch、模型网关和云模型。监控以下内容：

- 上传、解析、索引成功率和队列积压。
- 检索、重排和模型调用延迟。
- 空检索、引用核验失败、模型拒绝和系统降级。
- Token、模型调用次数、单份方案费用和部门预算。
- 权限拒绝、异常下载、文档数量、片段数量和索引增长。
- 方案采纳率、修改比例、退回原因和用户活跃度。

黄金评估集首期包含 100–200 个真实检索问题、20–30 份典型客户需求、10–20 份人工认可方案或章节、跨权负样本，以及扫描 PDF、复杂表格和图文 PPT 样本。

解析器、Embedding、Reranker、模型、提示词或检索参数升级必须通过同一套离线回归。

## 13. 测试策略

- **单元测试**：权限计算、版本状态、模板规则和引用映射。
- **契约测试**：Spring Boot 与 Python Worker、模型网关和 OpenSearch。
- **解析回归**：固定 Word、Excel、PDF、PPT、Markdown 和 PNG 样本。
- **检索回归**：Recall@10、nDCG@10、引用支持性和权限负样本。
- **端到端测试**：从上传资料到导出 Word。
- **安全测试**：提示注入、恶意文件、越权、路径穿越、输出注入和依赖供应链。
- **恢复测试**：PostgreSQL、对象存储和索引重建。
- **负载测试**：20 名试点用户并发上传、检索和生成。

生产发布门槛同时包含权限回归、检索质量回归和关键端到端测试。

## 14. 部署和运行

- 应用和 AI Worker 优先运行在 Linux 容器中。
- 若公司已有成熟 Kubernetes 平台，部署到现有集群；否则首期使用 2–3 台 Linux 虚拟机和 Docker，不为试点新建 Kubernetes。
- PostgreSQL、OpenSearch 和对象存储使用独立持久卷，建立实际恢复演练。
- 测试、预生产和生产至少逻辑隔离，生产客户文档不复制到测试环境。
- 在没有本地模型需求前不采购 GPU，优先复用现有计算和存储资源。

## 15. 实施阶段

### 阶段 0：立项与基线（1–2 周）

- 确定试点用户、业务负责人和知识管理员。
- 筛选 300–1000 份可信资料，建立基础分类与权限。
- 选取 30 份典型客户需求与历史方案。
- 记录当前耗时、返工和资料查找基线。
- 完成云模型供应商审批和第一版黄金评估集。

无可信资料集、业务负责人或可量化基线时，不进入开发。

### 阶段 1：知识底座（2–3 周）

完成钉钉 SSO、组织同步、ACL、文档版本、对象存储、解析/OCR、人工编目、发布、审计和失败处理。阶段演示必须证明有权用户可见、无权用户完全不可见。

### 阶段 2：可信检索（2–3 周）

完成混合检索、ACL 预过滤、二次校验、RRF、Reranker、来源定位和自动评估。权限测试未 100% 通过，或引用无法稳定定位时，不进入生成阶段。

### 阶段 3：方案生成工作台（3–4 周）

完成需求提取与确认、方案模板、大纲生成与确认、分章检索与生成、引用核验、在线编辑、版本比较、风险检查、Word 导出和用户反馈。

### 阶段 4：试点与硬化（2–4 周）

10–20 名用户使用真实但已脱敏需求，每周复盘失败案例，执行越权、提示注入、负载和恢复测试，统计提效、引用质量、采纳率和成本。业务负责人根据验收结果决定正式上线、延长试点或停止投入。

## 16. 团队与治理

建议团队：

- 产品/项目负责人 1 人。
- Java 技术负责人 1 人。
- Java 后端工程师 1–2 人。
- 前端工程师 1 人。
- Python/AI 工程师 1 人。
- 测试工程师 1 人。
- 运维与安全 0.5–1 人。
- 售前和产品领域专家 2–3 人兼职。
- 知识管理员 1 人兼职起步，正式上线后形成稳定职责。

每个知识空间必须有负责人，负责发布、授权、有效期和归档。公司建立知识分类与密级、命名与版本、发布与归档、模型供应商准入、配置变更、人工审阅责任和安全事件处理制度。

## 17. 成本控制

首期主要成本是研发与知识治理，不是 Token。运行成本包括云模型/Embedding/Reranker/OCR，数据库、检索、对象存储和备份，以及知识管理和评估。

控制方式：

- 需求与大纲确认后才开始长文生成。
- 按章节缓存检索和生成结果。
- 小模型执行分类、查询改写和字段抽取，大模型用于关键生成。
- 限制证据包体积和重复上下文。
- 为部门、用户和方案任务设定预算，记录单份方案成本。

## 18. 主要风险

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 历史资料质量差 | 结果过期或矛盾 | 先建 300–1000 份可信资料集，发布审核和有效期 |
| 权限失控 | 出现跨项目资料 | 默认不可见、双重校验和权限回归 |
| 生成内容不可信 | 引用不支持陈述 | 分章生成、引用核验和证据不足拒绝生成 |
| 员工不使用 | 采纳率低 | 嵌入真实工作流，每周复盘失败案例 |
| 范围失控 | 同时要求问答、报表和评审 | 仅验收方案生成闭环 |
| 供应商锁定 | 更换模型要改业务代码 | 模型网关和统一内部接口 |
| 双技术栈失控 | Python 开始承载权限和业务 | Python 只是无状态能力 Worker |
| 项目沦为演示 | 无基线或真实试点 | 每阶段设置退出门槛 |

## 19. 试点后决策

试点结束后只做三种决策：

1. **达标**：正式上线，逐步接入共享目录、项目系统和企业网盘。
2. **效率达标但质量不足**：继续改进解析、检索和知识治理，不扩展新场景。
3. **使用率或业务价值不足**：停止扩大技术投入，重新检查场景和业务流程。

达标后的扩展顺序是：数据源连接器、过期提醒与责任人、文档评审、项目报告，最后才评估知识图谱、Agent 自动化和模型微调。
